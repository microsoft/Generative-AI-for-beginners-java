# Покроковий посібник Foundry Local для Spring Boot

Запустіть невелику мовну модель на власному комп’ютері та викликайте її OpenAI-сумісний
REST-ендпоінт з Java-консольного додатку. Не використовується розгортання в Azure, вхід в Azure,
ключ API хмари або хмарне виведення. **GPT-5.6 Luna працює лише в Azure; не
налаштовуйте її як модель Foundry Local.**

## Версії та вимоги

| Компонент | Версія |
| --- | --- |
| Java | 21 або новіша |
| Maven | 3.6.3 або новіша |
| Spring Boot | 4.1.1 |
| OpenAI Java SDK | 4.63.1 |
| Foundry Local SDK (локальний REST-сервер) | 2.0.1 |
| Node.js (локальний REST-сервер) | 20 або новіша |
| Foundry Local CLI (опційно, окремий випуск) | 0.10.3 preview |

Spring Boot керує версіями Spring Framework, Jackson, JUnit та Maven плагіна.
У цьому прикладі безпосередньо використовується OpenAI Java SDK, а не Spring AI. Старе невикористане
властивість і репозиторій Spring AI milestone видалені.

Рекомендована стартова модель — **Qwen 2.5 0.5B**, CPU варіант
`qwen2.5-0.5b-instruct-generic-cpu:4` (близько 822 МБ у каталозі).
Вона не потребує GPU-провайдерів виконання. Можна вибрати інші підтримувані кешовані маленькі моделі.
Встановлення моделі та середовища виконання вимагає мережевого доступу;
підказки та виведення залишаються локальними. Foundry Local може все одно видавати мінімальну діагностику середовища
навіть із вимкненою необов’язковою телеметрією.

Виконуйте наступні команди з цього каталогу прикладу.

## Побудова та тестування Java

```powershell
mvn clean verify
```

HTTP-тести контракту запускають тимчасовий loopback сервер і перевіряють фактичний
OpenAI Java SDK. Вони охоплюють серіалізацію запитів, виявлення моделей, явний вибір моделі,
неоднозначні або пошкоджені списки моделей, HTTP-збої, порожні відповіді,
лише локальні URL, і поширення помилок командного рядка. Для них не потрібні модель або
мережевий доступ, крім встановлення залежностей Maven. Живий тест виконується за бажанням.

## Запуск локальної моделі

### Рекомендується: прив’язаний сервер SDK

Немає нативного Foundry Local Java SDK. Малий допоміжний Node.js розміщує
офіційний REST сервер SDK; додаток і запити чату залишаються на Java.

Встановіть прив’язані залежності середовища виконання:

```powershell
npm ci
```

Якщо Windows x64 не може дійти до NuGet під час нативного встановлення SDK, використовуйте надану
резервну версію. Вона завантажує відповідний офіційний архів середовища GitHub, перевіряє
SHA-256 контрольну суму релізу та розпаковує DLL біля нативного аддона. Не
вимикає TLS-валидацію, не потребує піднесення прав і не змінює вихідний код SDK.

```powershell
npm ci --ignore-scripts
pwsh -File ./scripts/install-foundry-runtime.ps1
```

Список моделей, вже кешованих на цій машині:

```powershell
npm run start:foundry -- --list
```

При першому запуску явно дозвольте завантаження маленької CPU-моделі:

```powershell
npm run start:foundry -- --model qwen2.5-0.5b-instruct-generic-cpu:4 --download --port 5273
```

При наступних запусках опускайте `--download` щоб вимагати кешовану модель:

```powershell
npm run start:foundry -- --model qwen2.5-0.5b-instruct-generic-cpu:4 --port 5273
```

Допоміжна програма віддає перевагу сумісній кешованій моделі, приймає псевдонім або точний ідентифікатор варіанту
і відмовляє в наявності відсутньої моделі, якщо не вказано `--download`. Вона реєструє лише
виконуючого провайдера вибраної моделі, коли це потрібно. Кешовані варіанти на GPU можуть
все ще потребувати сумісних пакетів та драйверів виконуючого провайдера.

Якщо порт 5273 зайнятий, передайте `--port 0` для доступного порту. Допоміжна програма виводить
`FOUNDRY_LOCAL_BASE_URL`, точний ідентифікатор `FOUNDRY_LOCAL_MODEL` та PID після готовності.
Використовуйте роздрукований ендпоінт у Java. Залишайте цей термінал відкритим під час роботи Java;
**Ctrl+C** зупиняє REST сервер і звільняє модель.

За замовчуванням кеш розташований у `~/.foundry/cache/models`. Щоб вказати
інший наявний кеш, встановіть `FOUNDRY_LOCAL_CACHE_DIR`. Логи та стан допоміжної програми записуються у
каталозі `target/foundry-local` цього прикладу. Зупиніть допоміжну програму перед запуском `mvn clean`.

### Опційно: Foundry Local CLI

CLI та SDK мають окремі випуски: CLI версії **0.10.3** пакує SDK **1.2.4**;
допоміжна програма вище використовує SDK **2.0.1**. Встановлення останнього CLI не означає встановлення
останнього SDK. Дивіться [примітки до випуску CLI](https://github.com/microsoft/Foundry-Local/releases/tag/cli-preview-0.10.3).

На Windows використовуйте команду персонифікованого встановлення, якщо CLI відсутній:

```powershell
winget install --id Microsoft.FoundryLocal --exact --source winget --scope user --silent --accept-package-agreements --accept-source-agreements --disable-interactivity
```

Або оновіть існуючу інсталяцію:

```powershell
winget upgrade --id Microsoft.FoundryLocal --exact --source winget --scope user --silent --accept-package-agreements --accept-source-agreements --disable-interactivity
foundry --version
```

CLI 0.10.x замінює старі команди `foundry service` на `foundry server`:

```powershell
foundry server start --port 5273
foundry cache list
foundry model load qwen2.5-0.5b-instruct-generic-cpu:4
foundry server status --output json
```

Команда `model load` потребує вже завантаженої моделі. Перевірте `foundry model --help` для
команд завантаження. Використовуйте фактичний ендпоінт із статусного виводу; CLI інакше
використовує автоматично призначений порт. Не запускайте CLI і допоміжну програму SDK
на одному порту. Після завершення:

```powershell
foundry server stop
```

## Запуск Java-додатку

У другому терміналі встановіть ендпоінт і точний ідентифікатор моделі, які видав ваш сервер:

```powershell
$env:FOUNDRY_LOCAL_BASE_URL = "http://127.0.0.1:5273/v1"
$env:FOUNDRY_LOCAL_MODEL = "qwen2.5-0.5b-instruct-generic-cpu:4"
mvn spring-boot:run
```

Або запустіть упакований додаток:

```powershell
java -jar target/foundry-local-spring-boot-0.0.1-SNAPSHOT.jar
```

Єдина точка входу Java — `com.example.Application`. Вона виводить вибраний
ендпоінт, фактичний ідентифікатор моделі, підказку й згенеровану відповідь, потім закриває контекст Spring
і HTTP клієнт. Невдала інференція або відсутність тексту відповіді викликає
вихід із помилкою замість успішного шаблону.

### Налаштування

| Змінна середовища | За замовчуванням | Призначення |
| --- | --- | --- |
| `FOUNDRY_LOCAL_BASE_URL` | `http://127.0.0.1:5273/v1` | HTTP ендпоінт loopback, включно з `/v1` |
| `FOUNDRY_LOCAL_MODEL` | Порожньо | Точний ідентифікатор моделі; інакше вибирається єдина заявлена модель |
| `FOUNDRY_LOCAL_PROMPT` | Одне речення з запитанням про локальні моделі | Підказка, що надсилається консоллю |

Еквівалентні аргументи Spring — `--foundry.local.base-url=...`,
`--foundry.local.model=...` та `--foundry.local.prompt=...`.
Приймаються тільки loopback HTTP ендпоінти. Віддалені/хмарні ендпоінти, вбудовані
облікові дані, рядки запиту та шляхи без `/v1` відхиляються.

Порожнє налаштування моделі працює лише, коли `/v1/models` рекламує рівно одну модель.
Оголошена модель необов’язково завантажена. Якщо рекламуються кілька моделей,
задайте точний завантажений ідентифікатор, а не покладайтеся на порядок у каталозі.

Запити використовують `temperature=0`, обмеження виводу 150 токенів, тайм-аут 120 секунд і
без автоматичних повторних спроб. Поле запиту `max_tokens` навмисне: воно
підтримується контрактом Foundry Local REST, хоча OpenAI Java відмовляється від нього.
це поле для новіших моделей хмарного типу. Ідентичність моделі походить із конфігурації або
виявлення, а не з власних тверджень моделі про себе.

## Жива перевірка

Коли локальний сервер запущено, виконайте всі тести, включно з тестом живої взаємодії за вибором.
Змініть порт кінцевої точки на значення, надруковане вашим сервером. Покажіть властивості
Maven у PowerShell у лапках:

```powershell
mvn "-Dfoundry.local.live=true" "-Dfoundry.local.base-url=http://127.0.0.1:5273/v1" "-Dfoundry.local.model=qwen2.5-0.5b-instruct-generic-cpu:4" verify
```

Тест живої взаємодії викликає `Application.main`, подає факт "Столиця Франції — Париж",
запитує місто та перевіряє, що фактично згенерований текст — `Париж`. Перевіряється
семантичний результат, а не лише успішний HTTP-статус.

Це перевірка інтеграції, а не бенчмарк точності. Під час перевірки модель 0.5B відповіла
на окремий запит "2 + 2" числом `3` через Java і напряму через REST. Не покладайтеся
на неї для арифметики чи фактологічної точності без незалежної перевірки; для обчислень
використовуйте детерміновані інструменти.

## Усунення неполадок

| Симптом | Перевірте |
| --- | --- |
| Відмова у з'єднанні | Чекайте повідомлення про готовність; використовуйте надрукований порт і шлях `/v1`. |
| Оголошено кілька моделей | Встановіть `FOUNDRY_LOCAL_MODEL` відповідно до точного ID підвантаженої моделі. |
| Відсутня модель | Використайте `--list` або явно дозвольте завантаження за `--download`. |
| Провайдер GPU не запускається або гальмує | Використовуйте малу CPU-модель. Кешована GPU-модель все ще потребує провайдера. |
| CLI залишається у стані `initializing` | Перегляньте `foundry server logs --lines 80`; зупиніть демон і використовуйте помічник SDK. |
| Помилка TLS/завантаження NuGet | Виправте мережевий доступ або використайте вказаний вище перевірений Windows x64 fallback. Не вимикайте TLS. |
| Порт зайнятий | Використайте `--port 0` та налаштуйте Java із надрукованим кінцевим пунктом. |
| Відсутні варіанти або пустий текст | Додаток навмисно завершується невдачею; подивіться логи моделі та виконання. |
